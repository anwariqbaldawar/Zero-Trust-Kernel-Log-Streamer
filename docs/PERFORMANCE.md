# Performance

What was measured, how it was measured, what the numbers do and do not include, and where the system
stops scaling.

---

## 1. Measurement method

| Aspect | Detail |
|---|---|
| Host | 2 vCPU sandbox, Debian 12, g++ 12, CPython 3.11, no kernel tracing available |
| Workload | 10,016 events: 10,000 benign plus 5 attack chains, generated by `src/engine/main.py` synthetic stream and by `tests/simulate_mcp_attack.py` |
| Rule set | the six shipped rules in `config/rules.yaml` |
| Latency instrument | `time.perf_counter()` around `RuleEngine.evaluate()` per event, aggregated into the `xsypher_rule_eval_seconds` summary |
| Two throughput figures | in-process replay over the same event stream, and end to end through a real `AF_UNIX`/`SOCK_SEQPACKET` socket |
| Repetition | several runs; ranges below show the spread |

**What these numbers exclude.** No BPF program runs, no ring buffer exists and no kernel traffic is
traced. The kernel-side cost of the tracepoints is not measured here and must be measured on the target
kernel with `bpftool prog profile` or `perf`. Treat the tables as the user-space budget, which is the
side that scales with rules and events.

**Why ranges.** p95 moved between 8.3 and 11.7 µs across runs and p99 between 14.8 and 17.3 µs on an
unloaded sandbox. Quoting a single figure would imply a precision the harness does not have.

## 2. Rule evaluation

| Metric | Observed |
|---|---|
| mean | 5.2 µs |
| p50 | 6.2 µs |
| p95 | 8.3 to 11.7 µs |
| p99 | 14.8 to 17.3 µs |
| max | 1.15 ms |
| budget | 500 µs per event |

The maximum is a cold-start artefact: the first evaluation of a rule touches interpreter fast paths and
builds string objects. In steady state the distribution is tight, and the 500 µs budget leaves roughly
30× headroom at p99.

Where the time goes, in order:

1. Subject resolution: basename and lowercase of `filename` or of the lineage node's `exe`.
2. Ancestry walk: one linked-list traversal of at most `max_ancestry_depth` nodes, done once per event.
   This is the only stage whose cost grows with process-tree depth.
3. Condition evaluation: set membership on pre-lowered frozensets, and `str.startswith` or `in` on
   pre-built tuples.

There is no regex in the hot path, no YAML parsing after startup, and no per-rule ancestry lookup. The
candidate index means an `execve` event evaluates two rules rather than six.

## 3. End-to-end throughput

| Path | Throughput | Per event |
|---|---|---|
| Engine, in-process replay | 136,000 to 151,000 events/s | 6.6 to 7.4 µs |
| Engine, through the socket, encode and decode included | 34,000 to 38,000 events/s | 26 to 29 µs |
| Simulation driver, including its own encode and send | 34,000 to 37,000 events/s | 27 to 29 µs |

The 4× gap between the two engine figures is the wire: encoding a 720-byte frame, a syscall per datagram,
`ctypes` `from_buffer_copy` on receive, and the asyncio loop's readiness notifications. In production the
collector produces frames at whatever rate the kernel emits, so the socket path is the relevant number.

End-to-end latency from detection to kernel map update, measured across the five attack chains:

| Chain | Path | Observed |
|---|---|---|
| A | shell breakout, cgroup quarantine | 2.1 to 2.2 ms |
| B | recon tool, pid quarantine plus address block | 2.2 to 2.3 ms |
| C | IMDS theft, cgroup quarantine plus block | 2.2 to 2.3 ms |
| D | credential harvest, pid quarantine | 2.2 ms |
| E | fileless staging, cgroup quarantine | 2.1 to 2.2 ms |

Roughly 2 ms of that is two process hops and two socket operations; the rule evaluation inside it is
microseconds. The practical implication is that a command reaches the kernel in the low single-digit
milliseconds, which is faster than the time a shell needs to fork and exec a second binary.

## 4. Cost model

Per event, steady state, on one engine core:

```
cost(event) ≈ decode                (constant, ~1 to 2 µs)
            + lineage upsert         (hash lookup, ~0.5 µs)
            + subject resolution     (constant, ~0.5 µs)
            + ancestry walk          (O(depth), 0 when no candidate rule needs it)
            + rule evaluation        (O(candidates for this event type))
            + audit append           (only on alert, ~20 to 40 µs with fsync)
```

The terms that grow are ancestry depth and the number of rules that share an event type. Both are bounded
by configuration, and both are visible in `xsypher_rule_eval_seconds` before they become a problem.

Binding constraints, in the order they are reached:

| Constraint | Limit | Signature | First fix |
|---|---|---|---|
| Socket and asyncio overhead | about 35,000 events/s per engine | `drops` in the collector status line | reduce event volume at the kernel filter |
| Python interpreter | about 150,000 events/s per core | CPU saturation on the engine | shard engines per node, or narrow the rule set |
| Ring buffer capacity | 16 MiB, about 25,900 records | `drops` in kernel metrics with a healthy engine | increase `XSYPHER_RINGBUF_BYTES`, then filtering |
| Map capacity | 16,384 pids, 4,096 cgroups, 8,192 addresses | `WARNING: policy cmd N failed` | raise the `max_entries` value in `xsypher.bpf.c` |
| Lineage graph | `--max-tracked`, default 200,000 | `xsypher_active_tracked_processes` at the limit | raise the limit or shorten the TTL |
| File descriptor limit | 64 clients, `LimitNOFILE=65536` | `accept4` failures | reduce engine count per collector |

## 5. Scaling

Enforcement capacity scales with nodes, not with a central component: each node has its own collector and
engine, and nothing is shared. In practice this means:

- **Per node**, one engine handles the traced syscall rate of that node. A typical container host with a
  thousand processes generates far fewer than 35,000 interesting events per second once the `openat`
  filter is in place, because the filter removes the dominant syscall class.
- **Event volume is dominated by `openat`.** If a host saturates the engine, the first measurement is the
  event-type breakdown from `xsypher_events_total{type}`. If `openat` dominates, the fix is the kernel
  filter, not more CPU.
- **Fleet correlation is out of scope.** There is no cross-node lineage, so a fleet-wide view is a
  function of the log pipeline, not of this system. Plan retention and query there.

A useful planning rule: size each node for three times the observed p95 event rate, and alert on
`drops > 0` sustained for five minutes rather than on CPU.

## 6. Reproducing

```console
$ PYTHONPATH=src python3 tests/simulate_mcp_attack.py
  workdir     : /tmp/xsypher-sim-w7d0s3a5
  benign evts : 10000
  chains      : 5 attack scenarios
  engine      : connected

  [1/3] streamed 10000 benign events in 0.28s (36,331 events/s)
  [2/3] injecting attack chains
        ok  chain A: MCP prompt injection -> interactive shell (2.1 ms)
        ...
  [3/3] verifying enforcement packets

  rule engine benchmark (in-process replay of the same stream)
        throughput       : 151,204 events/s
        rule eval p50    : 6.17 us
        rule eval p95    : 8.28 us
        rule eval p99    : 14.82 us
        rule eval max    : 1148.21 us
```

`./scripts/verify_and_benchmark.sh` runs the ABI parity check, the build when the toolchain is present,
the unit tests and the simulation in one pass, and reports unavailable stages as `SKIP` rather than
failing.

To measure the kernel side on a real host:

```bash
sudo bpftool prog show name xsypher_execve
sudo bpftool prog profile id <id> duration 10 cycles instructions
```

The number to watch is instructions per event for `xsypher_openat`, since it runs on every matching
`openat` on the host and is the only program whose cost is proportional to system-wide file traffic.

## 7. Known measurement gaps

- No kernel-side numbers in this repository's automated runs. CI has no BTF and no BPF LSM, so the load
  and hook paths are reported as `SKIP`.
- No sustained-load test. The simulation streams 10,016 events as fast as the socket accepts them, which
  measures peak rate but not behaviour over hours, including lineage growth and log rotation.
- No multi-client measurement. One engine is attached; the collector broadcasts to at most 64, and the
  cost per additional client is one `send()` per frame.
- `--fsync-alerts` was not benchmarked. It adds one `fsync` per alert, which at low alert rates is
  negligible and at high rates dominates; enable it when the log is the system of record, and measure
  before enabling it on a node that alerts continuously.
